# Добавление нового устройства

Это руководство описывает, как подключить к BetterYAM новую модель колонки
или другого устройства. Его можно использовать как последовательность работ
или передать coding-агенту вместе с репозиторием.

## Архитектура

Общий HTTP API и plugin runtime находятся в [`betteryam-runtime/`](../betteryam-runtime/).
Каждый daemon crate содержит entry point и адаптер устройства. Адаптер
предоставляет профиль и реализует аппаратные backend-интерфейсы из
[`device.rs`](../betteryam-runtime/src/device.rs).

Общий runtime не должен содержать модельные sysfs-пути, I2C-параметры или
фиксированное число LED. Для примеров см. адаптеры
[`yandexmini/adapter.rs`](../yandexmini/adapter.rs) и
[`yandexmicro/adapter.rs`](../yandexmicro/adapter.rs). Не переносите их
аппаратные параметры на новую модель без проверки.

## До начала работы

Зафиксируйте:

- точную модель и hostname-варианты, возвращаемые `uname -n`;
- архитектуру, ABI, версию ОС и доступный toolchain;
- способ подключения, установки, запуска daemon-а и необходимые права;
- аппаратные интерфейсы, системные устройства, утилиты и vendor API;
- функции, которые можно обнаружить и проверить;
- поведение при отсутствии оборудования, зависимости или разрешений;
- API-маршруты и возможности, необходимые существующим плагинам.

Не сохраняйте в репозитории credentials, токены, пароли, пользовательские
данные, дампы устройства или логи с секретами. Оставляйте только минимальные
обезличенные сведения, необходимые для реализации.

Установщики сейчас используют ADB, поддерживаемые ARM-архитектуры и выбор
daemon-а по hostname. Если новой модели нужен другой способ установки или
архитектура, одной записи в manifest недостаточно: отдельно спроектируйте и
проверьте изменения установщиков. Не направляйте модель на несовместимый
бинарник.

## Порядок реализации

1. **Сверьте контракты.** Прочитайте [`AGENTS.md`](../AGENTS.md),
   [`PLUGIN_API.md`](./PLUGIN_API.md), [`PACKAGES.md`](./PACKAGES.md) и
   [`DEPLOYMENT.md`](./DEPLOYMENT.md). Сверьте routes и profile с
   `betteryam-runtime/src/lib.rs` и существующими адаптерами. Не меняйте API
   плагинов или `byam` без отдельной необходимости и совместимого плана.

2. **Создайте daemon и адаптер.** Добавьте crate с коротким lowercase ID,
   включите его в workspace и добавьте зависимость на `betteryam-runtime`.
   Entry point передаёт runtime тип, реализующий `DeviceAdapter`. Оставьте
   аппаратный код в каталоге устройства. Если различаются только параметры,
   используйте общий backend с конфигурацией вместо копии драйвера.

3. **Сохраните API.** Предоставьте HTTP- и runtime-маршруты, необходимые CLI
   и существующим плагинам. Поддерживаемую, но недоступную функцию возвращайте
   с понятной ошибкой, а не как успешную заглушку.

4. **Объявите проверенные возможности.** В профиле укажите `id`, `model`,
   `architecture`, `led_count`, `features` и boolean `capabilities`.
   Включайте capability только при доступном backend-е. Сохраняйте принятые
   ключи, например `led.ring.rgb` и `led.ring.<count>`. Если доступность
   зависит от оборудования или состояния runtime, обнаруживайте её, а не
   выводите только из модели.

5. **Зарегистрируйте сборку.** Добавьте запись в корневой
   [`manifest.json`](../manifest.json): `device`, `models`,
   `manifest_path`, `binary`, `asset` и `target`. Указывайте точные hostname
   aliases. Установщик удаляет конечный сегмент `-XXXX` или `_XXXX` из четырёх
   заглавных букв/цифр, затем нормализует разделители и регистр.

   Пример записи; замените все значения на проверенные для нового устройства:

   ```json
   {
     "device": "vendor_model",
     "models": ["vendor-model", "vendor-model-revision"],
     "manifest_path": "vendor_model/Cargo.toml",
     "binary": "betteryamd-vendor-model",
     "asset": "betteryamd-vendor-model-aarch64-linux",
     "target": "aarch64-unknown-linux-musl",
     "filepath": "dist/assets/betteryamd-vendor-model-aarch64-linux",
     "sha256sum": null
   }
   ```

   `filepath` и `sha256sum` в исходном manifest — placeholders. Скрипт сборки
   формирует release manifest и подставляет фактические значения.

6. **Проверьте работу.** Если устройство доступно, установите daemon и
   проверьте выбор модели и аппаратные функции. Скрипт
   `tools/build-daemons.sh` собирает все записи manifest и создаёт
   `dist/manifest.json` и `dist/SHA256SUMS`. Не добавляйте `dist/`, бинарники
   или архивы пакетов в git.

## Проверки

Запустите подходящие workspace checks и shell syntax checks:

```sh
cargo fmt --all --check
cargo check --workspace --all-targets --target x86_64-unknown-linux-musl
cargo test --workspace --target x86_64-unknown-linux-musl
sh -n tools/build-daemons.sh
sh -n install.sh
```

Для release-сборки всех daemon-ов при наличии Docker:

```sh
BUILD_WITH_DOCKER=1 sh tools/build-daemons.sh
```

Без Docker локальная сборка использует доступные компиляторы
`arm-linux-musleabihf-gcc` и `aarch64-linux-musl-gcc`. Если target не удалось
собрать в текущей среде, укажите это явно. Не заявляйте аппаратную проверку,
если она не выполнялась.

В описании PR укажите проверенные hostname aliases, target и команду сборки,
добавленные capabilities, результаты проверки на устройстве и известные
ограничения.

## Запрос для coding-агента

Скопируйте этот запрос в coding-агент, работающий в корне репозитория, и
заполните сведения об устройстве:

```text
Добавь поддержку нового устройства в BetterYAM по docs/ADDING_DEVICES.md.
Изучи общий runtime, действующий plugin/API contract и adapters устройств.
Создай отдельный daemon и DeviceAdapter; не копируй hardware-параметры без
проверки, не дублируй runtime и не меняй API плагинов или permission model.
Объявляй только проверенные capabilities, добавь crate и точные hostname
aliases в manifest. Обнови тесты и относящуюся документацию.

Устройство: <производитель и модель>
Примеры `uname -n`: <точные hostname>
Архитектура / ABI / ОС: <данные или неизвестно>
Доступ к устройству: <есть / нет; доступные интерфейсы>
Требуемые функции и ограничения: <описание>

Запусти проверки из руководства и сообщи точные команды и результаты.
Отдельно укажи, что проверено на устройстве, а что осталось непроверенным.
Не включай секреты, пользовательские данные или неочищенные логи.
```
